mcp-use code mode

A program that throws should say why, on every executor

mcp-use code mode lets a model write JavaScript that calls MCP tools. The default executor runs it in Node's vm, and the E2B executor runs it in a remote sandbox. On E2B, a program that threw reached the caller as exit status 1, with its message and logs lost. This project diagnosed the mismatch with the E2B SDK's error handling, restored the real error message and logs, fixed a blocked-callback hang found on real E2B, and validated the patch with 23 targeted tests, 8 real E2B cases and the full client suite. The proposed patch is documented in mcp-use issue #3161 while awaiting maintainer feedback.

Scope and boundaries

  • Security boundary. The error marker carries a per-run id, which prevents accidental collisions. It is not an authentication boundary, because a program can read its own script. The patch reports the program's own error.
  • Validation environment. Real E2B runs used one region and the default sandbox size, with 8 cases per run. E2B usage cost was not measured.
  • Out of scope. Running several tool calls from one output chunk in parallel and serving a call split across chunks are separate behaviors, addressed by open PRs #2915 and #2984.
  • Test programs. The 60 programs were written by a language model, with the patterns chosen by hand.

Technical details

Why exit status 1

The executor writes the model's program to a file in the sandbox and runs node file.js with sandbox.commands.run(...). It then checked execution.exitCode !== 0. In e2b 2.32.0 that call does not return on a non-zero exit. It rejects with CommandExitError, which carries exitCode, stdout and stderr. The check never ran, the outer catch reported the SDK message, and the output was dropped.

const execution = await command.catch((e) => {
  if (isCommandExit(e)) return e;   // a real non-zero exit, with its output
  throw e;                          // anything else is still an error
});

Getting the message out

The wrapper that surrounds the program writes the thrown message on its own line, __MCP_PROGRAM_ERROR_<id>__ followed by the message as JSON. The id is new for every run, so printed text cannot match it by accident. The host reads the last line with this run's id, removes it, and keeps all other output as logs. The wrapper saves String, JSON.stringify, the output writers and process.exit before the program starts, because the program shares the process and may replace them.

A blocked callback, found on real E2B

A program that starts a tool call that never answers and then throws never returned from execute, even after the command timeout. The SDK's event loop runs await onStdout(chunk) for each output chunk and delivers the exit event through the same loop. The executor's callback awaited the host tool call, so one stuck call blocked the exit.

onStdout: (data: string) => {
  void this.serveToolCalls(sandbox, data);   // not awaited, and never rejects
},

The offline test sandbox first hid this, because it did not wait for callbacks. It now waits for each onStdout call before it reports the exit, like the SDK, so the regression test fails without the fix. A tool call that finishes after the sandbox is gone fails its write, and that error is dropped.

Validation

  • 23 targeted offline tests. They cover thrown values that cannot be converted, replaced globals, large output, printed marker text before and after the error line, a direct exit with stderr, whitespace-only output, a crash outside the wrapper, tool calls that answer and fail, and the pending tool call.
  • Real E2B, two runs of 8 cases. The first run passed 7 cases and exposed the blocked callback. After the fix all 8 passed, and the pending-call case returned in under 2 seconds. No sandboxes were left running.
  • Build, formatting, lint and the full client suite. The build succeeds, formatting and lint are clean, and all 473 tests in 70 files pass.

A reader can rerun the four-program comparison with no key and no network: sh reproduce/run.sh <path to an mcp-use clone>. It exports the base commit twice, applies patch/pr1-thrown-errors.diff to one copy, and runs both in Docker.

Engineering findings and boundaries

  • Found and fixed during validation: a tool call that never answers blocked execute from returning, a printed line shaped like the error marker could be taken for the error, a direct process.exit(1) that wrote to stderr reported that stderr as its error, whitespace-only logs were dropped, and the live test's cleanup could miss a sandbox if a case hung.
  • Existing behavior outside this patch: several tool calls in one output chunk run one after the other, a call split across chunks is not served, and log lines that contain the bridge marker text are removed from failure logs, as they already are on success. Open PRs #2915 and #2984 cover the first two.
  • Design boundaries: the marker is not an authentication boundary against a program that reads its own script. The live test's deadline cleanup covers sandboxes that exist when it fires, with the 60 second sandbox lifetime as the backstop. A tool call still running at cleanup writes into a closed sandbox, and that write error is dropped on purpose.
